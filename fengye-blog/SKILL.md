# 写作与润色

## 先读什么

- 先读用户正在改的文章，尤其是用户亲自写的前言、前后段落和最新改稿。局部润色以这些文字为准，保留人称、用词、解释密度和句子节奏。
- 用户在 2026-10-11 明确认可《手把手带工程同学从零实现一个完整的LLM（CS336）——Transformer篇》。写面向工程同学的原理教程、课程笔记时，优先读 [CS336 写作参考](references/cs336-writing-reference.md)，再按需读文章相应小节。
- 按文体选择旧文：[文风参考](references/style-guide.md) 保留了用户指定的其他文章。重新写整篇时选读几篇相关样本；已经读过且仍适用时复用，不为改一句话反复通读多篇。
- 优先使用本地博客源码。样本不存在时再从线上读取，不凭标题猜写法。
- 当前用户指令与最新改稿优先于历史范例。范例用来判断讲解方式，不能把整篇文章的所有句子都当成固定模板或永远正确的技术结论。

## 语气：直接、具体，保留作者原话

写给有工程经验、但未必熟悉当前理论的读者。用熟悉的词说明发生了什么、为什么这么算、怎么实现。解释清楚后就停，不为显得有深度再总结一遍。

- 用户要求润色时，先做小幅调整：修病句、去重复、接顺上下文。不要擅自改成另一篇文章，也不要把聊天里的整段答疑直接塞进正文。
- 可以自然使用“我们先看”“这里的”“比如”“下面”，也可以保留用户自己的口语。无需把每句话压短，不规定短句、连接词、口语词的数量。
- 个人经历、踩坑和感受只用用户提供的事实。没有素材就不加；用户删掉的回忆、类比或结尾不要再次补回。
- 避免“值得注意的是”“本质上来说”“最大的收获在于”这类空泛引导，以及“不是……而是……”式刻意对照。直接写具体内容；技术上的必要对比要说明差别和作用。
- 不机械禁用准确术语。“向量维度”等词可以用，但首次出现要解释；不要为了避词把技术意思改错。
- 后记简单交代做到哪一步、剩下什么、下一篇写什么即可。用户没要求感想，就不增加成长叙事、拔高或仪式化总结。

## 按读者的理解顺序解释

从读者眼前的操作、代码或公式引入名词，再解释用途。例如先说“这里的 + 就是残差连接”，随后说明它把什么加回什么、这样做有什么用。

复杂概念先在心里梳理读者的问题，再组织段落，不必把每节都写成同一个问答模板：

- 它解决什么问题，在哪一步加入？
- 输入是什么，具体怎么变，输出是什么？
- 哪些计算或形状不变，哪些结果会受影响？
- 相比前面已经介绍的方法，实际优势是什么？

不默认工程读者懂新出现的数学符号，也不反复解释已经讲清楚的基础概念。实现代码之后通常只需关键公式和短说明；删掉重复走一遍代码的数据流和没有新增信息的配图。

比较方案时明确比较对象。用户问“RoPE 相比把位置向量加到 token Embedding 上有什么优势”，回答应落在这两种方法的差别及其用途上，不能只各说一遍做法。

技术准确性优先：不要因为用户把 `d_model` 误认为 `seq_len` 就沿用错误；可以写成“每个 token 的向量包含 d_model 个数，seq_len 是 token 的数量”。未经确认的效果结论不写；必要条件放在结论旁简短说明，不追加长篇防御式免责声明。

## 公式、例子和计算过程

- 公式先说清在算什么，新符号在公式前后就地解释：代表什么对象、沿哪个方向计算、是否可学习、与代码里的哪个名字对应。
- 可以拆开就拆开。例如 RMSNorm 先解释均方根和 RMS 的计算，再说明每个分量除以 RMS、乘自己的缩放参数，不一开始给嵌套长公式。
- 用读者已经理解的形式。讲角度差时优先用余弦点积式，矩阵写法需要时再引入。公式里的双竖线要解释为向量长度，不能默认读者知道。
- 图和正文使用同一组符号、方向和公式。二维例子推广到高维时，补一句各分量对结果如何合并，避免把特例当成完整计算。
- 数字例子用来帮助算清一个步骤；讲一般规律、位置差或符号关系时用符号图，不为画图硬塞具体数字。
- 默认不加公式序号；用户要求的正式编号例外。
- 资源核算、习题分析按“要分析什么 → 怎么计算 → 简短结果”逐项写。允许有序列表，不禁止合理枚举。类似项目用紧凑表格比较，不重复长推导。
- 算数用脚本核对。参数共享、是否含偏置、batch 大小、仅矩阵乘法等会改变答案的口径用一句话交代；别把参数内存说成训练总内存。

## 资料如何进入文章

- 用户指定本地已有的讲义、PDF、代码时先定位并读相应内容，不能声称参考过未读资料。需要外部核实时优先原论文和作者说明。
- 用自己的组织方式说明原理，保证只读博客也能懂。不写“飞书讲义里”“按照 PDF 第几节”这类依赖读者另开资料的说明，不搬用讲义特有叙述。
- 用户明确要求引用题目时，保留指定语言的原文，用 Markdown `>` 引用；英文原题不要自行译成中文。引用和自己的分析分开。
- 文末补齐真正用到的课程、代码和原论文链接，明确哪个论文对应哪个方法。来源引用可以保留，正文不要写成文献综述。

## 配图

每张图只解决一个读者问题。能用一句话或公式说清的内容，不额外画流程图。

- 讲旋转、角度差时画坐标系、向量和必要的弧线；图中文字与相邻公式一致，不堆流程框、完整 Attention 步骤和方案对比。
- 图中文字默认使用苹方（PingFang SC）。检查实际导出结果，不只改字体声明；动图需要重新导出受影响的全部帧。
- 修改图片后确认文章引用了新文件，检查字号、符号、箭头、裁切和缩放后的可读性。
- 保留可维护的源文件，图片与动图放进文章同名资源目录，跟源码一起同步。

## 修改与发布

文章改动前先查看 Git 状态并重读目标段落。用户可能同时在编辑，不用旧副本覆盖整篇，不丢弃他们的修改。

局部任务只改相关内容；提交时明确哪些变更属于本次任务。用户明确要求同步所有正文和附件时，完整提交对应文章的已有修改，不再只提交 agent 自己写的几行。若仍有未提交内容，明确告知，不能宣称完整同步。

博客内容修改默认沿用已建立的发布流程；用户要求只草拟、本地修改或不发布时按用户要求。本次只修改 skill 时不发布博客。

1. 在 `hexo-source` 上修改 Markdown 与相关附件，检查引用和差异。
2. 在博客项目执行 `npm run clean && npm run build`。
3. 检查实际生成页面：公式错误、目录中的异常标题、列表/表格、图片和动图。涉及渲染问题时在浏览器查看，不能只看构建命令退出码。
4. 执行 `npm run deploy`，检查变更后提交相关源码及附件，并推送 `hexo-source`。不盲目 `git add -A` 混入其他工作。
5. 核对对应 `gh-pages` 提交的 GitHub Pages workflow 最终成功，再访问公开 URL 确认新内容。推送成功不等于发布完成。
6. 若 Pages 失败，查看具体 job 日志。旧构建 artifact 失效时完整重跑 build + deploy，不能只重复失败的 deploy。涉及部署、缓存等运维问题使用 `fengye-infra` 及其运行手册。

数学渲染注意：当前 Hexo/marked/hexo-xmath 链路下，公式中独占一行的 `=` 可能被当成 Markdown 标题；矩阵换行 `\\` 后紧跟字母也可能被错误转义。把等号放回表达式行，矩阵各行分行写，重新构建检查 `merror` / `Undefined control sequence` 和目录，再在线验证。不要靠修改 node_modules 留下无法复现的修复。

回报简短说明改了什么、检查了什么，并给文章路径、线上链接、源码和部署提交。发布未成功时准确说明当前状态。

## 交付前检查

- 读者是否无需跳到外部讲义就能理解？新术语和符号有没有就地解释？
- 有没有重复解释、机械总结、刻意口语化或虚构的作者经历？
- 对比是否回答了优势，而不只是列不同做法？计算口径和结果是否一致？
- 图是否真正帮助理解，且与正文公式一致？
- 是否保留了用户最新文字和明确删改？源码、附件和线上版本是否都确认过？

# 收藏页（Bookmarks）

## 概述

博客有一个独立的「Bookmarks」页面，专门展示通过 fengye-bookmark skill 收藏的外部文章。

关键设计：
- **完全独立于文章体系**：收藏不是 post，不会出现在首页、归档、分类中
- **数据驱动**：收藏列表存储在 `source/_data/bookmarks.yml`，模板自动渲染
- **导航栏入口**：`Bookmarks` → `/bookmarks/`
- **自定义主题模板**：`bookmark.pug` + `bookmark.styl`

## 收藏数据格式

数据文件：`source/_data/bookmarks.yml`

```yaml
- class_name: AI & LLM       # 分组名（可选，留空则不显示分组标题）
  class_desc: 人工智能与大模型  # 分组描述（可选）
  bookmark_list:
    - title: "文章标题"
      link: https://example.com/article
      description: 简要描述
      date: "2026-04-11"      # 注意：日期必须加引号，避免被 YAML 解析为 Date 对象
```

## 添加新收藏到博客的流程

当 fengye-bookmark skill 完成收藏后，将条目同步到博客：

1. **在 `bookmarks.yml` 中追加条目**
   - 找到合适的 `class_name` 分组，在 `bookmark_list` 末尾追加
   - 如果没有合适的分组，创建新分组
   - 日期用引号包裹：`date: "YYYY-MM-DD"`

2. **构建和发布**
   - 执行上方「发布流程」部分的命令

## 主题文件说明

以下文件是为书签页自定义添加到 Butterfly 主题的，**升级主题时需保留**：

- `themes/butterfly/layout/page.pug` — 添加了 `when 'bookmark'` 分支
- `themes/butterfly/layout/includes/page/bookmark.pug` — 书签页模板
- `themes/butterfly/source/css/_page/bookmark.styl` — 书签页样式
